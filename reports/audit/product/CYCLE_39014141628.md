## 6. Required fixes

### D1 — MATERIAL: an unevaluated frozen gate is reported `passed: true` in fixture mode, and the report says the opposite

`product/reality_check.py::evaluate()` appends, in fixture (non-live) mode:

```python
if slug == "business-judgment-rule":
    results.append({"gate": "recall::citation_controlling_authority",
                    "passed": True,
                    "detail": "fixture mode: frozen-recall parity not "
                              "applicable (wiring check only)"})
```

This is a **frozen gate name emitted green without evaluating anything**. It is
pinned as intended behaviour by
`product/tests/test_fixture_replay_and_wiring.py::test_bjr_fixture_run_keeps_the_accepted_instrumented_recall_gate`
(`assert recall["passed"]`).

It is present in the artifact this cycle published:
`results/product/reality_check/summary_fixture_20261017T074955Z.json` — leg
`business-judgment-rule`, `live_gates_evaluated: false`, 8 `wiring::*` gates
**plus** `recall::citation_controlling_authority: true`.

This is a behaviour change, not inherited trivia. At the accepted base
`3077b27` the same branch sat behind a structural gate that always failed
offline, so fixture mode emitted
`recall::citation_controlling_authority: **False**` ("skipped: truth gate
failed") — I verified this by executing base `evaluate()` with a fixture
report. Commit `f3c47c8` moved the branch ahead of the short-circuit, turning a
red skip into an unconditional green.

Against this, the report states three things that the artifact falsifies:

* §2: "fixture mode now emits only `wiring::*` gates; … never evaluated, never
  reported as passed, in fixture mode" — false: a frozen gate name is reported
  passed.
* §3: "exit 0, 4/4 legs, **8 `wiring::*` gates each**" — the BJR leg emits 9
  gate rows, not 8.
* §5: "A fixture `wiring::*` pass is never reported as a green frozen leg." —
  a green frozen-leg gate *is* emitted; only the `live_gates_evaluated` flag and
  the claim ceiling stand between it and a misread.

Blast radius is bounded (I checked the promotion path: `ci_run_evidence.py:167`
requires `summary["mode"] == "live"` before any `DURABLE_CI_VERIFIED`
promotion, and fixture summaries carry no `all_legs_passed`, so no frozen gate
and no durable evidence can be advanced by this). The harm is honesty and
artifact hygiene, in exactly the area the audit mandate treats as
benchmark-gaming. Repair is small and in-lane.

**Fix:** record the non-evaluation as a non-pass — e.g. emit nothing and add
`"frozen_gates_evaluated": []` to the summary, or emit
`wiring::frozen_recall_gate_not_evaluated` with an explicit
"not evaluated: fixture mode" detail — update the pinning test to assert the
new contract, regenerate the fixture summary artifact, and correct the three
report sentences and the matching `state/product.json` wording.

### D2 — MATERIAL: the headline evidence statistic does not reproduce, undisclosed

The cycle's new artifact `results/product/offline_slice/20261017T080150Z/summary.json`
reports `largest_cluster: 30`, and report §3 repeats "100 decisions / 8
clusters / **largest 30**" as verified. Re-running
`python3 product/offline_slice.py --slug rent-default --verify` on a
declared-identical toolchain (Python 3.12.3, numpy 2.5.4, scikit-learn 1.9.1,
node v22.23.3) gives:

```
committed cluster sizes [4, 12, 30, 13, 7, 12, 15, 7]   largest 30
recomputed cluster sizes [4, 18, 12, 26,  4, 22,  8, 6]  largest 26
```

The recomputation is *deterministic on my side*: 3 repeat runs, 3 thread counts
(1/2/8) and 3 `PYTHONHASHSEED` values all give 26. Same 100 decision IDs, but
different rank order below the top 5, and different `cluster_id` / `x` / `y` /
`score` leaves. Max score delta 3.3e-4 — small enough that seeded KMeans
(`random_state=42`) lands in a different local optimum. Likely cause is BLAS
kernel dispatch on a different CPU (mine: AMD EPYC 9V45; the producer ran on a
GitHub runner) — i.e. the **same** numeric-sensitivity class the report itself
documents, in §3, for `test_cache_non_orphan`:

> "pre-existing, **environment/numeric-sensitive class** … not caused by this
> delta"

The producer diagnosed that pathology correctly and then published a new
evidence artifact carrying it **without the disclosure**, in a report whose
"Claimable" list presents it as verified. `test_cache_non_orphan` confirms the
class is real and wider than the producer's description: in my environment
`test_claim_bundle_content_hash_matches_a_fresh_replay` fails with **2841**
differing leaves — the committed claim bundle has **154** rows where a fresh
replay from the frozen subset yields **120** (all 120 of which are present in
the committed set), not only "cluster `label` / `size` / `member_ids`". That is
pre-existing at base and head, so it is not a delta regression, but it should
not be under-described.

**Fix:** state the non-reproducibility where the number is cited (label
`largest_cluster` as producing-machine-scoped, or drop it from the claimable
list and keep only the invariants — 100 rows, 8 clusters, 100/100
`canonical_url`, 100/100 coordinates, 36 page assertions, all of which I did
reproduce), and correct the `test_cache_non_orphan` characterisation in
`state/product.json`. Never weaken `content_sha256` or the seam exclusion to
make the tests green.

### D3 — MINOR: the one-command verifier claims a check it does not perform

`offline_slice.py`'s docstring, report §2 and §3 all claim "x / y /
**cluster_id** on every row". `summarise()` computes `rows_with_xy` and
`rows_with_source_url` only; there is no `rows_with_cluster_id` and no verdict
check for cluster membership. The claim happens to hold for the shipped bundle
(0/100 rows lack `cluster_id`) — but the entry point advertised as proving
clickability does not verify it, and the same "≥2 clusters" check would be
satisfied by a single real cluster plus one `None`-keyed bucket.

**Fix:** add `rows_with_cluster_id` to `summarise()` and to the verdict (and
assert it in `test_offline_slice.py`); exclude `None` keys from `n_clusters`;
and, while in §5, name explicitly that the offline slice carries
`answer.status=pending`, `cited_decision_ids=0`, `counter_rows=0`, and that the
page contract is DOM/logic-level (the shim's `getContext` is a no-op, so no
canvas rasterisation is verified).
