## 3. Required fixes

### 3.1 MATERIAL — the "lightning is dead" provenance is contradicted by the repository's own evidence, and this cycle made it load-bearing and machine-readable

The cycle states as fact (report §1; `state/product.json →
v49_dead_model_filter_20261016.problem_addressed`; seam docstring) that
`nemotron-3.5-lightning-free` and `nemotron-3-ultra-free` are "the two models
the 2026-10-16 health snapshot proved dead", citing
"`state/model_health.json`, run 38919946016, 15:01:41Z … lightning FAIL
(exit 124)".

Auditor findings:

1. **Run 38919946016 does not exist in this repository.** No commit, tag, ref
   or blob mentions it. The only model-health artifact anywhere in the object
   store is one file.
2. **That one artifact says lightning is alive.**
   `main:state/model_health.json` = commit `37c1ed9` "control: refresh free
   model health **38933507133**", `last_checked_at: 2026-10-16T16:40:57Z`:

   ```
   opencode/nemotron-3-ultra-free    catalog_present=true  tool_probe=FAIL  exit=124
   opencode/nemotron-3.5-lightning-free catalog_present=true tool_probe=PASS  exit=0
   opencode/mimo-v2.6-flash-free     PASS 0
   opencode/space-bunny-free         PASS 0
   opencode/longcat-2.5-preview-free PASS 0
   ```

   That snapshot was written **15 minutes before this cycle's own legs ran**
   (16:56:04Z) and 31 minutes before `state_updated_at` (17:12:19Z).
3. **The repository's own history contradicts it too**:
   `results/product/reality_check/rent-default_live_20261014T113201Z.json`
   records `answer_model: opencode/nemotron-3.5-lightning-free` completing a
   full leg in 281.065 s.
4. **It is now load-bearing and published.** `apply()` filters on this
   set at call time, and `known_dead_models` is written into every bundle's
   `provenance.product_audit_seam`. Auditor demonstration of the consequence,
   with the control-plane health list installed:

   ```
   healthy_models() -> ['opencode/mimo-v2.6-flash-free', 'opencode/space-bunny-free',
                         'opencode/longcat-2.5-preview-free']
   => lightning dropped although the control plane says tool_probe PASS
   ```

   The behaviour is *safe* (it can only remove candidates, never add a bad
   one), so this is not a correctness-of-output failure. It is a false
   provenance claim in a claim-bearing artifact, plus a lost healthy fallback
   on a path whose binding constraint is the 300 s latency gate.

**Required fix (concrete, same-cycle):** either remove
`opencode/nemotron-3.5-lightning-free` from `KNOWN_DEAD_MODELS`, or keep the
exclusion but cite the evidence that actually justifies it (the component's own
60 s adversarial-budget evidence for that model) and record explicitly that the
newest control-plane snapshot reports `tool_probe: PASS` for it. The same
correction must land in the seam docstring, `reports/product/CYCLE_38933925523.md`
§1, and the `state/product.json` problem statement, because all three currently
assert a snapshot that is not in the repository. `nemotron-3-ultra-free`
(`FAIL 124` in both the absent and the present snapshot) is correctly
classified and needs no change.

### 3.2 MATERIAL — the headline latency improvement is attributed to a mechanism that was inactive in both compared runs (post-hoc causal claim)

Report §4 and `state/product.json` both carry the note that the corporate leg
"dropped from 276 s (prior cycle) to 188 s **because dead models no longer burn
timeouts**".

Auditor reconstruction of both runs' model chains:

| run | report | `workflow_override` | `model_order` in provenance | answer / adversarial | total_s |
|---|---|---|---|---|---|
| prior cycle | `corporate-…_live_20261016T160526Z` | *(absent)* | `[mimo, space-bunny, longcat, muse-spark]` | space-bunny / space-bunny | 276.119 |
| this cycle | `corporate-…_live_20261016T165604Z` | `true` | `[mimo, space-bunny, longcat, muse-spark]` | space-bunny / space-bunny | 188.727 |

In the prior run there was no workflow override, so `healthy_models()` already
returned the pinned `MODEL_ORDER`, which contains **no dead model**. Computing
`_ordered_answer_models()` over both configurations yields the *same* chain
(`mimo → space-bunny → …`) and the same adversarial preference; both runs ended
on the same model for both calls. The dead models therefore could not have been
attempted in either run, and cannot explain an 87 s difference. The most
plausible explanation — mimo hitting its 120 s provider timeout and falling
back to space-bunny in both runs, with different provider latency — is
unattributed.

**Required fix:** restate the note in the report and in
`state/product.json` as an unattributed run-to-run difference (and say what
the provider attempt chain actually shows), or drop the causal clause. Keep
the honest part: this cycle's four legs are 142.9–188.7 s, comfortably inside
the 300 s gate.

### 3.3 MODERATE — the instrument the cycle's evidence rests on has no drift guard

`WORKFLOW_MODEL_OVERRIDE` is the entire evidentiary basis for "green locally
under the durable workflow's **exact** model-list condition". It is a
hand-copied constant with no test. The repository already contains the exact
pattern for this — `product/tests/test_reality_check.py` parses
`.github/workflows/product-reality-check.yml` and fails when the matrix
questions or the truth-gate literals drift — and this cycle added nothing in
that file. If the control plane reorders or edits that list (it is rewritten
whenever model health is refreshed), the flag will silently keep reproducing a
stale condition while the report keeps claiming exactness.

**Required fix:** add a parity test asserting
`reality_check.WORKFLOW_MODEL_OVERRIDE == <parsed workflow override block>`
(fail-closed), mirroring `test_runner_legs_match_workflow_matrix`. Optionally
add one asserting `KNOWN_DEAD_MODELS` does not contradict
`state/model_health.json` when that file is present.
