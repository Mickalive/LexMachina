## 3. Findings, severity-ranked

No blocking defect. Nothing found requires a repair round.

### F1 — Unrecorded (and partly spliced) numbers in the canonical state *(minor, provenance)*

`state/product.json → history.v51_deltas.progressive_slice.negative_result` and report §1 state:

> "288 concurrent /api/health probes, 0 failures, server alive after enrich, answer ready, **7 citations**"

No artifact of this cycle contains either figure. The cycle's own recorded probe counts are **259**
(cold), **89** (v2), **5** (fixture); the recorded runs with 7 citations are v2 (89 probes) and the
ones with 259 probes cite 8. The sentence splices two runs, and the probe count is unrecorded. My
own drive of the same blocking path measured 299 probes / 0 failures, so the *substance* is
corroborated — this is an annotation gap, not a fabrication. The same applies to the pre-change
baseline (136.79 s start / 150.70 s enrich / 136.61 s upstream / 101.69 s model / 49.00 s
hydration), which is quoted as measured in the report, in `state/product.json → …progressive_slice.why`,
and in three source docstrings plus two test docstrings, with no artifact behind it. My measurement
of the old blocking enrich (146.89 s) corroborates it within ~3%; the 136.79 s cold start is not
independently reproducible from here (my warm start was 0.54 s).
*Advisory:* record the baseline drive as an artifact, or mark those figures as cycle-local
observations that were not persisted, and cite a recorded probe count instead of 288.

### F2 — The first map a jurist sees is single-language and single-channel *(minor, undisclosed limitation)*

`first_page_config` runs `stages=("search",)`, `lang_max_pages=0`, `max_requests=1`. In both the
producer's v2 artifact and my run, the first page is **38/38 French** with a single channel
(`{"search": 38}`), while the finished map is DE 73 / FR 30 / IT 36 / unknown 47 across
`search`, `search.language_filter`, `leading_case`, `citation.outgoing` and `citation.incoming`.
The report's honest-limits section says the first page is "one upstream page (≈38–50 hits) … a real
subset of the same retrieval" — true, and I confirmed all 38 survive into the final 194 — but it
never says that the map drawn first is monolingual in a trilingual court system.
*Advisory:* one line in §5 / state. This is a first-impression caveat for the pending human gate, not
a correctness defect.

### F3 — No offline test pins the cycle's central mechanism *(minor, coverage)*

All 21 new tests in `test_progressive_query.py` run `retrieval_mode="fixture"`, and
`_retrieve_first_page` in fixture mode bypasses `first_page_config()` entirely (it replays the whole
fixture — 105 decisions in the fixture smoke, which is why `assert len(decisions) >= 50` passes
trivially). So the offline suite never exercises the bounded single-request retrieval that is the
whole point of the cycle; only the live smoke does. My cold run proves the mechanism works
(`network_calls: 1 / budget_max: 1`), so this is a coverage gap, not a defect.
*Advisory:* one pure-function test asserting `first_page_config(...).max_requests == 1` and
`stages == ("search",)` pins it for free.

### F4 — Two absolute claims that are not literally true *(minor, wording)*

* Report §2.3: "Enrich waits for a running expansion … so the answer is **never** generated from the
  partial first-page candidate set." `_await_expand` returns as soon as the expand job is not
  `running` — including when it is `error` — so an enrich that follows a *failed* expansion answers
  from the first page. The UI surfaces the expansion error before starting enrich, so no user is
  misled; the absolute should read "unless the expansion failed".
* The UI pill says "10 contre-autorités" (`isCounter` excludes `cited`) while the bundle and
  `run_status` say 16 (any status ≠ `none`). Both are internally consistent; the two numbers are
  never reconciled for the reader.

### F5 — Observed in my run only, pre-existing, outside this cycle's diff *(observation)*

My independent run produced an answer containing the inline token
`[vd_findinfo_Décision___2013___894]` (accented `é`) where the canonical bundle id is
`vd_findinfo_D_cision___2013___894`. The decision is real and its substance is grounded, the prose is
rendered as plain text (not linkified), so nothing breaks — but `citation_validation`
(`mode: strict_local`, `api_base: null`) validates only the structured `cited_decision_ids` and
never flags prose tokens that do not byte-match a bundle id. Producer runs show 0 such tokens
(7/7 and 8/8 resolve). Belongs to the accepted generative-audit component, not to this cycle.

### Not found (attacks that came back clean)

No frozen benchmark, threshold or success rule was touched; the accepted server-contract test was
**extended**, not weakened (it now asserts the 202 + poll contract *and* the `wait_s` blocking
form). No historical claim-bearing result was overwritten or deleted (all `results/`/`reports/`

has no consumer outside `product/` — the reality-check legs, latency budget and both CI workflows
