## 1. Query-map MVP capability audit

This audit examines the shortest user-visible capability of the query-map MVP: does real/cached OpenCaseLaw input produce a source-linked result bundle and clickable map, and are zero-cost/source-validity claims true?

### 1.1 Real OpenCaseLaw input → source-linked result bundle + clickable map

**Test:** `python product/query_app.py --port 8805` (one-command local server, stdlib ThreadingHTTPServer), then `GET /api/query/start?q=Responsabilite+penale+de+l%27entreprise+selon+l%27art.+102+CP&n=150`.

**Result:** The API returns a valid `query_result_bundle` with provenance indicating `mode=live`, `fixture_mode=false`. All 38 first-page decisions carry `canonical_url` fields linking to `mcp.opencaselaw.ch` decision URLs. The progressive expansion adds 156 decisions (total 194) while preserving geometry: `points_moved=0`, `points_displaced_by_refit=0`, cluster count stable at 8.

**Timing (cold start, no prior cache):**
- `GET /api/query/start`: **0.188 s total** = 0.022 s upstream OpenCaseLaw + 0.166 s local geometry
- `GET /api/query/expand` (background): 0.377 s upstream + 0.111 s local, 156 decisions added, map stability preserved
- `GET /api/query/enrich` (pollable job): model `opencode/nemotron-3-ultra-free`, answer ready after ~118 s, 7 cited ids, 12 counter-status decisions

**Clickable map verification:** `node product/verify_query_page.js` against the enriched bundle → **PASS 16 assertions**. All DOM checks pass: baseline renders one row per decision with source links, map<->list toggle works, product status survives re-render, canonical URLs are present and valid.
