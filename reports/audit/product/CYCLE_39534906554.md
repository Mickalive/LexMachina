## 1. Scope of Audit

Per the workflow mandate: **audit the shortest user-visible capability first** — does real/cached OpenCaseLaw input produce a source-linked result bundle and clickable map, and are zero-cost/source-validity claims true?

The audit focuses on the **progressive query pipeline** introduced in `product/query/progressive.py` and served via `product/query_app.py`:

1. **Stage 1 (First Page):** `run_query_first_page()` — one bounded OpenCaseLaw search page → renderable map in ~200ms (fixture) / ~90ms (live cached)
2. **Stage 2 (Expand):** `expand_query_bundle()` — full retrieval merged into the same map geometry
3. **Stage 3 (Enrich):** `enrich_query_bundle()` — lazy evidence hydration, generative-audit answer, counter-authority pass, adversarial retrieval

The UI (`product/static/query.html`) consumes this via a three-stage job API (`/api/query/start` → `/api/query/expand` → `/api/query/enrich`) with polling `/api/query/status` and resume via `/api/query/bundle`.
