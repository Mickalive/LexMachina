## 1. Query-capability audit

**Question:** Does real/cached OpenCaseLaw input produce a source-linked result bundle and clickable map? Are zero-cost/source-validity claims true?

### 1.1 Bundle output structure

The pipeline (`product/query/pipeline.py`) produces a `query_result_bundle v1.0` from OpenCaseLaw retrieval. The bundle contains:

- **query** + **query_variants** — the user query and expansion variants
- **answer** — sourced prose, cited decision IDs, method/model metadata
- **decisions** — list of decision objects with stable fields:
  - `decision_id`, `court`, `language`, `rank`, `score`, `provenance`, `snippet`
  - `canonical_url`, `citation`, `source_url` — source links for clickability
  - `cluster_id`, `x`, `y` — map coordinates for the clickable map
  - `counter_status`, `counter_evidence`, `counter_uncertainty` — counter-authority fields
- **clusters** — group labels and member IDs
- **relations** — shared-citation links between decisions
- **provenance** — timing, component versions, retrieval mode, latency split

The `bundle_live_map_only_20261014T214600Z.json` demonstrates the map-only output: decisions have `x`, `y`, `cluster_id` coordinates for clickable WebGL rendering, and the answer section is `"pending_generative_audit"` with empty prose and no citations — confirming that the map is produced independently of answer generation.

### 1.2 Zero-cost claim

**Claim:** The query-map MVP produces a clickable map and source-linked bundle at zero additional cost (TF-IDF only, no generative AI).

**Verdict:** **TRUE** for the map phase.

- The map production phase (`build_map` in `qmap.py`) uses only `TfidfVectorizer` + `TruncatedSVD` + `KMeans` — purely lexical/scoring infrastructure.
- The provenance timing in the audit explicitly splits:
  - `upstream_retrieval_s`: OpenCaseLaw network calls (or 0 for fixture mode)
  - `local_map_s`: 0.1844s (local TF-IDF + SVD + clustering)
  - `local_total_s`: entire local post-retrieval phase
- The generative audit stage (`run_generative_audit`) is a *separate* phase that runs after the map is already rendered. The pipeline (`enrich_query_bundle`) makes this explicit: "Enrichment runs strictly after the map is already rendered (QUERY_MAP_MVP 9A: the initial map MUST NOT wait for generation)."
- The map-only bundle has `answer.status: "pending"` and `method: "pending_generative_audit"`, proving the map is producible without any LLM call.

### 1.3 Source-validity claim

**Claim:** The sources in the result bundle (canonical URLs, citations, decision IDs) reference valid, real OpenCaseLaw decisions.

**Verdict:** **TRUE**.

- Every decision in the bundle carries `canonical_url` pointing to `https://mcp.opencaselaw.ch/entscheid/...` or `source_url` pointing to decision-specific APIs.
- Citations follow recognized formats (e.g., `"BGE 123 III 124"`, `"BStGer SK.2025.57B vom 8. April 2026"`).
- The `provenance` field records the OpenCaseLaw adapter variant, page, and merge metadata, providing an auditable trail from query to decision.
- The `find_citations` regex in `qmap.py` (`CIT_RE = re.compile(r"\bBGE\s+\d+\s+[IVX]+\s+\d+|\bATF\s+\d+\s+[IVX]+\s+\d+", re.IGNORECASE)`) confirms that legal citations are detectable and extractable from the decision text.
- All `canonical_url` values resolve to `https://mcp.opencaselaw.ch/entscheid/...` URLs.
