## Attack log (adversarial checks and their outcomes)

1. **Leakage / hardcoding hunt** — no decision_id, bundle id, row count or
   supported-set membership is hardcoded in `decide_label`; the gate reads only
   the row's own fields plus the frozen rules and the question anchor profile.
   The 5 emitted rows are an *output* of the gate (equal to the rubric's
   supported set), not an input. **No leakage found.**
2. **Benchmark gaming ("support 1.0 by abstaining on everything")** — the
   candidate does cut yield 65→5, but this is precisely the trade the charter's
   hypothesis mandates ("That lowers label YIELD, which is the correct trade…
   publish support rate, abstention count and yield side by side"), the
   non-vacuity controls would have voided a vacuous tie (they score 0.0 vs the
   candidate's 1.0), and the claim ceiling explicitly forbids claiming the 1.0
   is a property of the decisions. The 1.0 is structural by design — the
   charter's acceptance test (2) *requires* the gate to be the frozen
   domain-anchor + intent-marker conditions — and the producer discloses this
   openly ("an emitted label is supported by construction"). Honest, in-scope,
   not gaming.
3. **Post-hoc tuning** — impossible by construction: no tunable parameter
   exists; the five scoring modules are byte-identical to the accepted cycle
   branch; the rubric file is hash-pinned and re-proved before scoring.
4. **Weak-baseline attack** — the incumbent baseline is the *accepted* 5/65
   from `LABEL_HALF.json`, reproduced here (not a re-derived or weakened
   strawman); divergence would have been reported per row and was not needed.
5. **Prettiness-as-quality** — no UI/rendering code was written; the deliverable
   is a decision function + tests + contracts, judged only on frozen-rubric
   numbers.
6. **Claim-ceiling attack** — ran the snapshot's 5 forbidden regexes over every
   team artifact: 0 hits; no artifact asserts a specific decision IS
   supporting/contrary/limiting; the component confirms or abstains on the
   product's own issued labels.
7. **Boilerplate confound** — the `pointer_only` / `procedural_formula_no_intent`
   steps use the *frozen* lexicons only; synthetic boilerplate rows abstain
   (unit-tested); no bespoke boilerplate list was authored.
8. **Scope-creep / duplication** — writes confined to the team's own frontier
   paths; no touch of product lanes, promoted teams' deliverables, or the
   measurement charters' artifacts; adoption explicitly left to Core Product.

## Non-blocking advisories (recorded, not required for integration)

- **A (disclosure, already in-claim):** support 1.0 among emitted is a property
  of the *emission policy under the frozen rubric*, not a discovery of new
  supported authority. The component's product value is the counted abstention
  (60) and the published support/yield trade. The claim ceiling already binds
  this; Product must keep publishing support rate, abstention count and yield
  together.
- **B (per-bundle reading):** "strictly better" holds per bundle in de and it;
  in fr the candidate abstains on all 15 rows (incumbent had 0 supported there),
  so bundle-level supported count is unchanged at 0 while no unsupported label
  ships. The charter's operative comparison (overall 5/65, INVERTED=0, no rubric
  edit) is met; per-bundle abstentions are honestly published in the artifact.
- **C (report prose error):** `REPORT.md` states the swapped-evidence control
  gate reason as `no_intent_marker`; both the committed `HEAD_TO_HEAD.json` and
  my independent re-run show **`pivot_absent`** for all 5 control rows. The
  authoritative artifact is correct; only the report parenthetical is wrong;
  the outcome (control strictly below, gate refuses all 5) is unaffected.
- **D (harness hardening):** `_compare_to_accepted` keys rows by decision_id in
  a dict, so 4 duplicated decision_ids collapse 65 rows to 61 compared keys
  (`n_rows_matched: 61`), while `REPORT.md` says "all 65 rows". I independently
  proved full 65/65 multiset equality (including the duplicates), so the claim
  is substantively true; a future harness should compare multisets.
- **E (drop-in scope):** `STATUS_TO_LABEL` defaults an *unknown* proposed status
  to `limiting` if all gates pass; the documented contract scopes input to
  candidate rows carrying one of the six mapped counter statuses. The Product
  adapter must feed only proposed-counter rows (as the contract already
  prescribes).
