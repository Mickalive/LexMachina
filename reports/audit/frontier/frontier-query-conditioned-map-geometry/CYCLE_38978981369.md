## 7. The cycle's new finding, verified — and the defect this audit found next to it

### 7.1 The team's finding is TRUE and correctly routed (verified at source)

```
query.html:141  const COLORS=["#2459a8",…8 entries…];
query.html:188  ctx.fillStyle=COLORS[(p.cluster_id??0)%COLORS.length];
query.html:240  '…style="background:"+COLORS[c.cluster_id%COLORS.length]…'   // legend: clusters[] only
```

- JavaScript `%` truncates toward zero: `(-1) % 8 === -1`, `(-47) % 8 === -7` (the team's `js_mod` implements exactly this and pins it in a test; my own arithmetic agrees).
- `COLORS[-1]` is `undefined`; assigning `undefined` to `ctx.fillStyle` is an invalid value the canvas **ignores**, so the previous point's colour persists.
- Independently confirmed on the served bundles: the negative-id set is **exactly** the un-hydrated shell set (`detail_status != "search_hit"`), 47 / 49 / 47 rows, and the additive `unclustered` flag is set on exactly those rows. Every emitted cluster record has a non-negative id (min 0), so the legend is indeed unaffected.
- Confirmed this is an **adoption-time** hazard, not a live production bug: the shipped geometry derives cluster ids from sklearn labels / nearest centroid (`qmap.py:353-390`) and never emits a negative id. The team's characterisation is right.
- Sibling exposure the record does not name: the same `%` expression exists in the rendering lane's own adapter, `frontier-query-map-ui` → `ui/canvas2d_renderer.js:531` and `product/static/bundle_adapter.js:94`. The owning-lane note points at that lane but the record cites only `query.html`.

### 7.2 DEFECT (material): the accepted integration contract promises a coordinate range the component does not deliver

`INTEGRATION_CONTRACT.json → output_contract.decisions[].x` states:

> `"x": "float, rounded to 4 decimals, [-1,1] (V1) or [-1,1] (V2)"`

## 8. Two self-reports that overstate what the measurements support

**(a) Exposed-row counts.** `README.md` and `REVERIFICATION_38978981369.json → exposed_rows` state **47/214, 49/217, 47/211**, and the README says *"Every unclustered-shell point is therefore painted in whatever colour was drawn before it."* The team's own artifact is more precise and disagrees: `negative_ids_index_outside_palette` = **42 / 43 / 42**, and its own test asserts *"almost every shell id misses the palette"*. The difference is exact and explainable — ids that are exact multiples of the palette length (8) index a real colour, so `cluster_id = −8` renders as `COLORS[0]` (valid, but wrongly equal to cluster 0) rather than inheriting the previous colour. 47/49/47 is the count of rows *carrying* a negative id; 42/43/42 is the count whose fill actually breaks. Both numbers should be stated, with labels.

**(b) "Byte-identical" reproduction.** `REVERIFICATION_38978981369.json` sets `criterion_level_identical_to_accepted_run: true` and lists the two `SCORES_*` files as differing *"only in wall clock and stamped run id"*. On this machine — same declared stack, which I installed independently: python 3.12.3, numpy **2.5.4**, scipy **1.18.1**, sklearn **1.9.1**, all four matching `ENVIRONMENT.json` exactly — **all 99 verdicts and all pass counts reproduce exactly, but four criterion *values* do not**:

| Criterion | max cross-environment drift | Bit-identical criteria |
|---|---|---|
| `PROJ_KNN10` | 1.38e-03 | `COHERENCE_QUERY_LANG`, `COHERENCE_QUERY_TERM`, |
| `PROJ_RANK` | 7.79e-04 | `STRUCTURE_LARGEST`, `LABEL_CONTENT_FRACTION`, |
| `STRUCTURE_SEP` | 1.71e-04 | `LABEL_JACCARD`, `RELATIONS` |
| `PROJ_SPEARMAN` | 1.05e-04 | |

Thread count is **not** the cause: forcing `OMP/OPENBLAS/MKL_NUM_THREADS=1` reproduces the 4-thread values exactly. The drift is confined to the four criteria that pass through `sklearn`'s pairwise **cosine** distances on SVD coordinates inside the vendored scorer, and it affects the **incumbent** numbers too — so it is scorer numerics, not variant geometry. Impact: the nearest decision margin anywhere in the run is **0.0169**, i.e. **12× the largest observed drift**, and every verdict and count is identical. No score, bar, total or outcome is affected. But `ENVIRONMENT.json`, added this cycle precisely so that "a reproduction elsewhere" could tell whether the rule is deterministic, does not record the variable that actually moves the numbers, and no artifact discloses that these four values are environment-sensitive. Honesty about reproducibility is the whole point of that file; it currently over-promises.
