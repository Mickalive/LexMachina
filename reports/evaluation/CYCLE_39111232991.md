## 2. The measurement gap this cycle found and closed

**The lane had no claim-bearing gate that scores the PRODUCT against a frozen id set.**

- All **40** gates of the frozen retrieval benchmark
  (`evaluation/retrieval_gate`, `frozen_sha256 187b0e54b03b326c62d45d8ba48fc78dc88501086761cd91a84c304a7478ba72`)
  draw their rows from `evaluation.retrieval_gate.client.SearchClient` — i.e. from plain
  OpenCaseLaw searches. The frozen spec's own `baseline_definition` says so: *"the same
  OpenCaseLaw result set WITHOUT query-map reranking, lexicon expansion or citation-neighbourhood
  expansion"*.
- The only product-side output that benchmark exposes,
  `record["exploratory_product_cache_comparison"]`, reads the product's raw
  `results/product/query_cache` envelopes, is labelled `TIER = EXPLORATORY` **in the frozen spec
  itself**, and is never read by `gates.evaluate()`. It cannot move `overall_pass`.
- The other packet-touching evaluators (`packet_admission_conformance`,
  `packet_lineage_sweep`, `served_bundle_scope`, `served_packet_transfer`, `rebuild_preflight`,
  `frozen_bars/*`) address served packets for **lineage, scope, label and geometry**. None of
  them measures recall of a frozen authority set against a served bundle.
- `evaluation/benchmark_retrieval_counter_authority.py` — the existing three-leg falsifier —
  falsifies the **frozen gates** (instrument non-vacuity). It does not falsify the **product**.

**Consequence, stated plainly:** a product could ship a served bundle that retrieves strictly
*less* of the frozen known counter-authority set than the plain OpenCaseLaw top-50 it wraps, and
every accepted gate in this lane would stay green. That is exactly the failure the Master
Prompt's retrieval-first doctrine exists to prevent — *"optimize recall before map
aesthetics"*, *"preserve lower-ranked candidates that may represent contrary or minority
lines"*, *"a visualization cannot reveal an authority that retrieval failed to find"*.

This cycle closed that gap. It is the only new measurement.

## 3. The freeze (written BEFORE the scorer executed)

`evaluation/PRODUCT_COUNTER_RECALL_HYPOTHESIS.json`
sha256 `2e94d1c6f65af304fa6345be00e8a29b34016012a4c3e04ee4bb36bbafb10c38`

**Question.** Does the shipped query-map product's served bundle retrieve the frozen
controlling-authority set and the frozen known counter-authority set, at least as well as the
plain OpenCaseLaw result set it wraps?

**Success rule, frozen verbatim.**

> PASS_NO_PARITY_REGRESSION (exit 0) if and only if, for every MEASURABLE cell,
> `product_recall >= baseline_recall` on BOTH frozen id sets. Any measurable cell with
> `product_recall < baseline_recall` on either set is FAIL_PARITY_REGRESSION (exit 1). No
> measurable cell at all is NOT_MEASURED (exit 2).

The rule is **a-priori and contains no tuned constant**. It is forced by the architecture
documented in `ARCHITECTURE.md` (*"OpenCaseLaw retrieval / citation expansion → … → independent
counter-authority pass"*) and by this lane's own directive (*"Baseline should be the same
OpenCaseLaw search/result set without the additional query-map/counter-authority machinery where
practical"*). A layer that returns strictly fewer of a known id set than the layer it wraps has
by construction added no recall. The only threshold is `product >= baseline`.

**Analyst mapping, frozen before execution — disclosed as an assumption, not a product fact.**
The product's served question ids are not the frozen spec's slugs:

| frozen slug | served question id | basis | strength |
|---|---|---|---|
| `rent-default` | `fr-bail-entretien` | same rule: lease termination for rent arrears, art. 257d OR / CO | strong |
| `corporate-criminal-liability` | `de-kapitalverletzung` | same subject: criminal liability of corporate organs, art. 102 OR / Kapitalverletzung | strong |
| `petty-theft-dismissal` | `it-responsabilita-medica` | **different subject matter** (medical liability vs. petty theft under art. 337 StGB) | **WEAK — disclosed as weak** |
| `business-judgment-rule` | — | no served counterpart | **NOT_MEASURED, recorded explicitly, not silently dropped** |

The weak cell is admissible **only in the product-vs-its-own-baseline direction**, which is
precisely the frozen rule, because the same subject weakness is present on both sides of the
comparison. Per-cell results are published so a reader can reject any single mapping without
rejecting the rest.

**Honest pre-execution disclosure.** Before the freeze was written, a reconnaissance pass was run
in the shell: it printed the raw hit/miss counts of the accepted matcher over each served bundle.
The benchmark was not implemented and no verdict existed. The disclosure records exactly what was
seen, *before* the rule existed, so a reader can judge the freeze against the observation rather
than the other way round. It could not have chosen the rule: the rule is `product >= baseline`,
which is architecture-forced, and it contains no constant that was fitted. Precedent:
`evaluation/reality_gate` and `evaluation/retrieval_gate` both carry an equivalent
`pre_freeze_disclosure` field.

### The finding

**On every measurable cell, the product's served bundle retrieves strictly fewer of the frozen
controlling-authority and known counter-authority ids than the plain OpenCaseLaw result set it
wraps.**

- `fr-bail-entretien`: counter set **1 of 9** product vs **3 of 9** baseline. The two
  baseline-only authorities are `gr_gerichte_PKG_2010_20` and `zh_mietgericht_MB170006-L`.
- `de-kapitalverletzung`: authority set **0 of 2** vs **2 of 2**; counter set **0 of 6** vs **4 of 6**.
- `it-responsabilita-medica`: authority set **0 of 2** vs **1 of 2**; counter set **0 of 9** vs **7 of 9**.

### Why this is not a harness artefact

1. **The accepted matcher fires on the product's own id format.** Frozen `bge_BGE_117_II_415`
   (alnum core `117ii415`) resolves against product row `decision_id = 'bge_117 II 415'`,
   `docket_number = '117 II 415'`. If the matcher were blind across the BGE-style/ATF-style
   difference, the measured zeros would be a formatting artefact. It is not, and this is pinned
   by `test_accepted_matcher_resolves_at_least_one_frozen_id_in_a_product_bundle`.
2. **The baseline-only ids are real baseline rows.** Asserted per id against the baseline pool
   and its matcher cores.
3. **Row scale is comparable.** Product 217 / 214 / 211 decisions vs baseline pool 240 rows per
   slug. This is not a "the product showed fewer rows" artefact.
4. **The benchmark is deterministic** — repeated execution reproduces the verdict byte for byte.
