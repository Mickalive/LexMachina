## 1. The falsification: a cached replay could report a latency PASS

This is the headline result and it is a **negative** one about the lane's own deliverable.

### What happened

`results/evaluation/retrieval_benchmark/38939239917.json` records finding **F5**: the 24-search live retrieval pass measured **256.827 s against the frozen 240 s budget**, so `latency::full_pass_under_budget` **FAILED**. The cycle report's own recommendation is:

> *"re-run this frozen retrieval benchmark from cache to confirm the recorded verdict is stable"*

Doing exactly that, with `--offline`, erased the finding:

```
python -m evaluation.retrieval_gate.run_retrieval_benchmark --offline
→ pass_a_mode=offline_replay   pass_a_wall_seconds=0.067
→ latency::full_pass_under_budget:  FAILED (live)  →  PASSED (replay)
```

**Cause.** No gate read `pass_a_mode`. A cached replay replaces the live wall time with the cache-read wall time (0.067 s), and the gate compared that against the budget. A measurement of the disk was accepted as a measurement of OpenCaseLaw. Two independent defects combined:

* `evaluation/retrieval_gate/client.py:192` — `if out.latency_seconds is None and not out.from_cache` leaves a replayed search's latency as `None`, so `latency::search_under_budget` degraded to `not_measurable` with the misleading reason *"no successful search carries a latency"*.
* `evaluation/retrieval_gate/run_retrieval_benchmark.py:264-268` — offline mode overwrites `pass_a_wall_seconds` with the replay wall.

Recorded verdict: 12 failed / 24 passed / 4 n-m. Replay verdict: **11 failed / 24 passed / 4 n-m** — the only difference is the erased failure. `overall_pass` stayed `false` in both, so a summary reader would not have noticed; a per-gate reader would have seen a frozen failure disappear.

### Fix (strictly anti-falsification)

`evaluation/retrieval_gate/gates.py` — new `LIVE_PASS_MODE = "live"` and `_pass_a_not_live()`. A latency gate may return a pass/fail verdict **only** when pass A was a live pass; otherwise `not_measurable` with an explicit reason. Content gates are untouched, because replaying the same raw bytes legitimately re-measures content.

**No budget was moved, and the recorded live verdict is byte-identical after the change** — verified by re-scoring:

```
python -m evaluation.retrieval_gate.run_retrieval_benchmark --rescore \
  results/evaluation/retrieval_benchmark/38939239917.json
→ exit 1, rescored verdict byte-identical to the stored verdict
```

After the fix the same replay yields `latency::search_under_budget=None` and `latency::full_pass_under_budget=None`, both with the reason *"`pass_a_mode='offline_replay'` is not `'live'`"*. Durable evidence: `results/evaluation/retrieval_benchmark/38945976309_cached_replay.json`.

**Second line of defence (self-audit finding).** The mode flag binds only what a record *declares*. A record claiming `pass_a_mode: "live"` while carrying a hand-edited `pass_a_wall_seconds` would still be scored against the budget and could pass it. `gates.record_latency_plausibility()` closes that: on a live record the wall time may not be shorter than the sum of the live per-search latencies it contains, and may not exceed the record's own `started_at → generated_at` span. On the recorded run that catches a forged 0.067 s (247.646 s of latencies inside it) and a forged 99999 s (record span is 257 s). Like the id-hygiene measurement it is deliberately **not** a gate — adding a gate would change the recorded verdict and destroy its byte-identity test. It is wired into `python -m evaluation.lane_suite` and pinned by three tests.

Regression tests: `tests/evaluation/test_retrieval_gate.py` — `test_cached_replay_cannot_report_a_latency_pass`, `test_cached_replay_does_not_hide_a_recorded_latency_failure`, `test_record_without_declared_pass_mode_is_not_measurable_for_latency`, `test_content_gates_still_work_from_a_cached_replay`. An undeclared mode is treated conservatively (not measurable), so an old record cannot certify a latency verdict by omission.

## 3. The reality benchmark had no record-integrity check

The retrieval gate recomputes its stored verdict byte-identically. The reality benchmark had no equivalent, and its tests never re-read a committed record — so a hand-edited record (one `passed` flipped to `true`) would have passed every test in the lane.

`run_benchmark.check_record_integrity()` (cycle 38945976309) audits a stored record: pinned frozen digest, counts recomputed from the artifact list, `failed_gates`/`not_measurable_gates` consistent with the gate outcomes, passing gates carrying blank detail, failing gates carrying detail, `not_measurable` always carrying a reason, `artifact_passed` and `overall_pass` consistent with the failures.

It goes further and **re-derives `passed` from the gate's own `measured` payload**, which needs no mount: `latency::under_budget`, `corruption::clean`, `recall::*`, `truth::*` (both kinds), `multilingual::*`, `structural::bundle_validation_clean`, and the undetectable-language case. A flipped verdict leaves its own contradicting measurement in the record.

Tamper classes proven detectable (each has a test):

| tamper | detected by |
|---|---
| `latency::under_budget` FAIL → PASS | *"recorded passed=True but its own measurements say 463.773s vs 300.0s budget"* |
| `recall::citation_controlling_authority` FAIL → PASS | *"0 hit(s) of 5 required"* |
| `truth::art257d2_end_of_month` FAIL → PASS | *"no matched phrase (None)"* |
| blanked failure detail | 19 problems |
| removed `not_measurable` reason | 49 problems |
| dropped artifact / inflated `n_evaluated` | count mismatches |
| foreign frozen digest / `overall_pass` flipped / excluded artifact gains a verdict | header and scope checks |

### Claim ceiling of the check itself — and the gaps found by attacking it

`check_record_integrity` proves **internal consistency**, not provenance or measurement authenticity. Adversarial probing of this cycle's own check found **three tamper classes it does not catch**, now enumerated in code as `check_record_integrity_known_gaps()` and pinned by `test_check_record_integrity_declares_its_own_untamperable_classes` (which also *demonstrates* each one, so the list cannot quietly shrink):

1. **Deleting a whole artifact and renumbering every count passes.** The check counts what is there; it cannot know what should be there. Catching it needs the evidence tree, i.e. a re-execution against the ACCEPTED product mount.
2. **Flipping a `structural::*` failure to a pass passes.** Those gates carry no `measured` payload, so nothing in the record contradicts the flipped verdict. This is material: **six of the recorded failures in 38934722443 are `structural::counter_classifications_supported`**.
3. **Rewriting a gate's `measured` values alongside its flipped verdict passes.** The measurements are carried on trust — `latency::under_budget` flipped to a pass together with `total_seconds: 1.0` is undetectable here.

The one structural gate that *does* carry a payload (`structural::bundle_validation_clean`, via `validation_errors`) was brought under the recheck this cycle. Its test is synthesised rather than taken from a record, because no committed record contains such a failure — it passes everywhere on the accepted packet, and a test that waited for one would silently never run.

All three committed reality records (38920872324, 38934722443, 38945976309) pass with **0 problems**.
