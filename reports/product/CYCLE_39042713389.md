## 3. What this cycle changed (runnable delta)

### 3.1 The audit environment is now triaged, not reported as product failure

`core-lane.yml` has **no `actions/setup-python` and no `pip install`** in either the team or the audit
job, so the audit checkout may legitimately have no numpy. Reproduced in this checkout *before* any
fix: six of nineteen checks died with `ModuleNotFoundError` and printed as plain `FAIL` —
`readiness_claim_guard` among them, with an **empty reason**, because it caught the import error and
returned `ok=False`. To an independent auditor that is indistinguishable from a broken product.

Now, in `product/audit_pack.py`:

* a missing import is `BLOCKED_MISSING_DEPENDENCY`, counted separately from failures
  (`n_blocked_missing_dependency` / `blocked_ids`), with `blocked_by` and a one-line bootstrap command
  per blocked check;
* new exit-code contract — `0` all ok, `1` product failure, `2` dependency-blocked (nothing proven
  false), `3` harness error;
* new `CheckBlocked` exception: a check that cannot conclude declares itself blocked **and still
  reports its dependency-free measurement**. `readiness_claim_guard` uses it, so its claim scan is
  published instead of being converted into a verdict;
* `dependency_status()` / `missing_dependencies()` / `bootstrap_dependencies()` preflight, exposed as
  `--deps` and `--bootstrap-deps {auto,on,off}` (writes nothing inside the repository, so it cannot
  trip the audit job's write-scope check);
* the console prints a real reason for every failing check instead of an empty string, and `--out`
  outside the repository no longer crashes the summary line.

Measured before/after in a genuinely dependency-free interpreter:

| --- | --- | --- |
| reported `FAIL` | 7 (one with an empty reason) | **0** |
| `BLOCKED_MISSING_DEPENDENCY` | n/a (not modelled) | 6, each naming its module |
| exit code | 1 (= product failure) | **2** (= nothing proven false) |
