## 2. Durable product delta: a late expansion could erase an enriched answer

Exercising the shipped progressive server instead of re-diagnosing accepted
work exposed a real defect in `product/query_app.py`:

1. `expand` and `enrich` jobs both write the run's stored bundle.
2. A client could start an expansion *after* enrichment completed (the public
   API allows it and the UI can retry).
3. That late `map_expanded` bundle overwrote the `complete` bundle, so
   `/api/query/status` reported `jobs.enrich.status=done` and
   `answer.status=ready`, while `/api/query/bundle` returned
   `answer.status=pending` with no cited decisions — a page reload silently
   lost the sourced answer.

Reproduced deterministically against the shipped server record, then fixed
with a monotonic stage guard in `product/query_app.py`:

```
first_page / map_ready (0)  <  map_expanded (1)  <  complete (2)
```

A lower stage may never replace a higher one. An incoming later stage still
replaces an earlier one, so normal enrichment is unaffected.

Regression coverage: `product/tests/test_query_app_stage_guard.py`

- the state-machine invariant with synthetic bundles (the exact losing write);
- explicit stage-rank ordering;
- the shipped server over a real socket: start → expand → enrich (`wait_s`) →
  public re-expand → `/api/query/bundle` still carries `phase=complete`,
  `answer.status=ready` and cited decisions.
