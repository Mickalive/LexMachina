— absolute filesystem paths — inside the hashed payload.

## 2. The fix

### 2.1 `product/replay_bundle.py`

* `TIMING_PATHS` keeps its honest name and its five wall-clock entries.
* New `CACHE_ROOT_PATHS` names the two cache roots; `content_sha256` rewrites
  them to the constant `CACHE_ROOT_TOKEN`. A different cache root can no longer
  move the hash; a different **key count** still can, because `n_keys` is a
  separate field and is not touched.
* Defence in depth: `_scrub_machine_paths` rewrites any other machine-specific
  absolute filesystem path to `ABSOLUTE_PATH_TOKEN`, so the next field someone
  adds cannot silently re-break portability in the same way.

**The scrub is deliberately narrow, and that was a real correction inside this
round.** The first implementation scrubbed *every* string beginning with `/`.
`hashed_payload_paths` immediately showed the over-reach: the recorded upstream
endpoints `provenance.stage_notes.{citations,leading}.endpoint` — `/citations`
and `/leading-cases` — were being collapsed onto one token. That would have
made two distinct claim-bearing values hash identically, i.e. bought portability
by discarding evidence. `is_machine_path` now excludes
`API_ENDPOINT_PREFIXES`, and a test asserts the endpoints are still inside the
payload.

The scrub's classifier is a separate, directly tested function:

| value | `is_absolute_fs_path` | `is_machine_path` |
|---|---|---|
| `/home/runner/…/query_cache` | yes | **yes** → neutralised |
| `C:\Users\runner\query_cache` | yes | **yes** → neutralised |
| `//mcp.opencaselaw.ch/decisions` | no (protocol-relative URL) | no |
| `https://mcp.opencaselaw.ch/decisions` | no | no |
| `/citations`, `/leading-cases`, `/decisions` | yes | **no** → kept |
| `bge_BGE_142_IV_333` | no | no |

### 2.2 Disclosure instead of trust

`inspect_bundle` now publishes `hashed_payload_paths`
(`{machine_paths, api_endpoints, timings_dropped}`), so a reviewer sees *what*
was neutralised rather than taking the hash's word for it. On the claim bundle:

```
machine_paths: [".provenance.cache_stats.root",
                ".provenance.retrieval.remote.cache_stats.root"]
api_endpoints: ["….citations.endpoint", "….leading.endpoint", (×2 nested)]
timings_dropped: 5
```

`cache_root` in the CLI output is now reported repo-relative, so the tool's own
output is machine-stable too.

## 3. Regression tests named by the gate

Three new tests in `product/tests/test_cache_non_orphan.py`:

1. **`test_content_hash_is_invariant_under_a_rewritten_cache_root`** — rewrites
   both cache roots to a foreign absolute path and requires an unchanged hash;
   then changes a decision's citation and requires the hash to **move**. The
   second half matters: without it, "make the hash path-independent" could be
   satisfied by hashing nothing.
2. **`test_committed_bundle_has_no_unaccounted_absolute_paths`** — the only
   machine paths in the committed payload are the two declared cache roots, and
   `/citations` and `/leading-cases` are still present. This is what stops the
   next field from re-creating D1 silently.
3. **`test_is_machine_path_separates_paths_from_upstream_endpoints`** — the
   classifier table above.

Plus one that makes a *stronger* guard than before (§5.1) and two for the
disclosures in §5.
