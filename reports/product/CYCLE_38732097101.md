## 3. New executable surface (the time-to-clickable delta)

### `product/human_gate_evidence.py` — admissibility scanner (new)

One command an auditor can run:

```
python product/human_gate_evidence.py      # exit 0 = admissible, 1 = a blocking defect
```

It judges the canonical and simulated directories by **role** (directory name), so it also works on a copy or a
synthetic tree. Blocking codes: `contradictory_claim_ceiling`, `simulated_in_canonical_dir`,
`real_record_in_simulated_dir`, `missing_finalized_by`, `missing_run_id`, `non_positive_wall_clock`,
`bundle_not_verified`, `implausible_decision_count`, `unconfirmed_owner_session`, `claims_human_gate_ready`,
`test_scratch_session_id` (canonical only), `unreadable_record`. Warnings are reported, never silently dropped.

Run against the pre-repair tree it reproduced the audit's F2 verdict independently:

```
[blocking] contradictory_claim_ceiling: session_session-20261015T113329Z.json — simulated=true but the
           claim ceiling does not say SIMULATED SESSION: 'human gate EVIDENCE only: this record documents…'
[blocking] contradictory_claim_ceiling: session_session-20261015T114037Z.json — …
-> NOT ADMISSIBLE
```

### `product/human_gate_session.py` — one-command gate runner (new)

The remaining milestone is a *comparative* human session, and the mechanical part of it was four manual steps with two
ways to fail (forgetting provenance → exit 7; identifying the wrong bundle → a session bound to nothing). The runner
closes the loop:

```
python product/human_gate_session.py --port 8791 --run-id <run> --operator <name> --owner-session
```

It serves the product, prints the four gate questions and the "a *no* is a valid result" contract, watches for the
harness export, **binds the draft to the exact bundle that was served** (read from the same in-memory run registry the
UI reads — the owner never has to pick a bundle by hand), finalizes with attested provenance, then runs the evidence
scanner and prints the verdict. Subcommands: `finalize <draft>` (no server), `check` (scan only).

### A defect this cycle caused, found by running it, and fixed

The first end-to-end rehearsal of the runner wrote a machine-authored record into `results/product/human_gate_sessions/`
— it satisfied every structural rule the finalizer had, because structure cannot tell a person from an agent. Root
cause: `serve()` dropped `--out`. Both halves are fixed: the `--out` flag is threaded through, and the canonical
directory now requires the explicit `owner_session_confirmed` declaration, so that class of accident is refused
(exit 8) rather than merely avoided. The stray record was removed from `results/`; its bytes are preserved outside the
repository for this report. **No machine-generated session record exists anywhere in `results/` after this cycle** —
which is also what the audit's BLOCKED trigger requires.

### 7.1 Required fix 1 — the process-global pool teardown (falsification-verified)

**Defect.** `product/human_gate_session.py::serve()` ended with
`POOL.shutdown(wait=False, cancel_futures=True)` on `query_app.POOL`, a `ThreadPoolExecutor` created at
`query_app` import time and shared by the whole interpreter. The new test
`test_serve_returns_9_when_no_session_is_exported` calls `serve()` in-process; from that moment every later
`POOL.submit` raised `RuntimeError: cannot schedule new futures after shutdown` and `/api/query/start` answered
HTTP 500 — 8 pre-existing server tests collected after `test_human_gate_session.py` failed.

**Repair.** `serve()` now owns only what it created: it still shuts down the HTTP server it made, and it no longer
touches `query_app.POOL`. Process-global teardown moved to the `__main__` entry point, the only place that owns the
interpreter the pool lives in, so the CLI keeps its fast cancelled-queue teardown while no in-process caller can be
poisoned. A new regression guard,
`test_serve_does_not_shut_down_the_process_global_job_pool`, asserts both the mechanism (the executor still accepts
a submission after `serve()`) and the user-visible symptom (a server started afterwards still answers
`/api/query/start` with `map_ready`).

**Evidence.** The 13 MVP modules, default collection order, CI-pinned venv (pytest 9.1.1, numpy 2.5.4,
scikit-learn 1.9.1):

| condition | result |
|---|---|
| before the repair, at `aae6f90` | 8 failed, 227 passed, 1 skipped (the audit's number, reproduced) |
| repair applied | **236 passed, 1 skipped, 0 failed** (237 collected: 236 + 1 skip + the new guard) |
| defect re-injected into `serve()` | **9 failed, 227 passed, 1 skipped** — the 8 original failures *plus* the new guard, which fails on the exact `RuntimeError: cannot schedule new futures after shutdown` |

The repair is therefore load-bearing, and the guard fails on its own, not only through cross-module ordering.
