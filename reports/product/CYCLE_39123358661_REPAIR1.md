## 1. DEFECT A — the refusal demonstration was time-dependent

**The false claim** (report §1 and the diagnosis artifact's
"the FAIL-ledger poisoning path is closed" evidence):

> `python3 product/cycle_verify.py --only regression --run-id 99999999999 --write`
> → refused, exit 1, no file written

**Recomputed here, before any change** — it does not reproduce:

```
$ python3 product/cycle_verify.py --only regression --run-id 99999999999 --write
[PASS] (regression) the run under test introduces no failing test id absent from the baseline
[PASS] (regression) the published pass/fail arithmetic closes on the set relation it measured
[PASS] (regression) both roots the set relation was measured at are published with it
PASS: 3/3 claims verified                                    exit 0
wrote results/product/cycle_verify/CYCLE_99999999999_cycle_verify.json
```

**Root cause of the defect** (not of the invariant): that command FAILs only
while the **newest** `CYCLE_*_regression_scope.json` records a new failure. When
cycle 39119287975 committed its clean artifact, the newest became clean and the
demonstration silently turned into a PASS. The refusal mechanism in
`cycle_verify.py::main` was never wrong — the auditor verified it sound — but a
demonstration whose truth depends on a moving neighbour cannot support a report.

**The fix, in three parts:**

1. **A pinned failing artifact.** `product/data/regression_fail_fixture/CYCLE_39116225867_regression_scope.json`
   is a byte-identical copy of the committed `CYCLE_39116225867` regression
   artifact — the one that genuinely records `n_repaired_only = 1`. No new data,
   no synthetic FAIL; the failure is a real committed measurement.
2. **`--regression-dir`.** `cycle_verify.py::main` gained one additive flag that
   repoints the `regression` check at another committed artifact set. It changes
   where the verdict comes *from*, never how the verdict is handled. The
   override is restored in a `finally`, so a demonstration flag can never leak
   into a later invocation in the same process
   (`test_an_override_in_flight_is_restored_even_when_a_check_raises`).
3. **The demonstration, corrected.** Report §1 now publishes exactly:

```bash
python3 product/cycle_verify.py --only regression \
  --regression-dir product/data/regression_fail_fixture \
  --run-id 99999999999 --write
# FAIL: 2/3 claims verified
# REFUSED: verdict is FAIL, so this ledger was NOT written to the canonical
#          directory results/product/cycle_verify ...
# exit 1; nothing written to the canonical directory
```

Verified live in this cycle, in-process and as a subprocess
(`test_the_demonstration_runs_as_the_documented_command`).

**The timing dependency is recorded, not hidden.** The original unpinned
invocation is now asserted to be a **PASS** against the canonical directory
(`test_the_original_time_dependent_invocation_is_now_a_documented_pass`), with
its twin asserted to FAIL under the pinned fixture. Identical arguments, the only
difference is which artifact set the verdict is read from — which is the proof
that the refusal is about the verdict, not the arguments.

## 2. DEFECT B — a hand-written artifact classification had drifted

**The false claim** (report §1 step 3 and the diagnosis artifact's
`produce_pass_pass`): `CYCLE_39116225867_regression_scope.json` produces
PASS/PASS for `check_regression_set_relation`.

**Recomputed here** — it produces **FAIL/PASS/PASS**. Its `set_relation`
records `set_difference_repaired_only_NEW_FAILURES = ["product/tests/
test_cycle_verify_is_a_gate.py::test_committed_artifact_is_a_pass_and_says_what_
it_is_not"]`, so the first claim fails.

**Root cause of the defect:** there was no way to ask the question.
`check_regression_set_relation` only ever reads the *newest* artifact, so
"which artifacts would produce PASS/PASS" had to be answered by copying the
gate's three expressions into an ad-hoc script. The copy drifted, and nothing
re-derived it.

**The fix — the classification is now a command, and the ledger enforces it:**

- `product/regression_set_relation_matrix.py` (new, runnable) classifies **every**
  committed artifact with the gate's own predicate, **imported, never copied**:

```bash
$ python3 product/regression_set_relation_matrix.py
9 committed regression artifact(s) in results/product/regression
predicate: product/cycle_verify.py::regression_set_relation_rows

artifact                                       claim1  claim2  claim3  all
CYCLE_39048942749_regression_scope.json        FAIL    FAIL    FAIL     FAIL
CYCLE_39051003925_regression_scope.json        FAIL    FAIL    FAIL     FAIL
CYCLE_39060279436_regression_scope.json        PASS    PASS    PASS     PASS
CYCLE_39063665073_regression_scope.json        PASS    PASS    PASS     PASS
CYCLE_39087917357_regression_scope.json        PASS    PASS    PASS     PASS
CYCLE_39094983039_regression_scope.json        PASS    PASS    PASS     PASS
CYCLE_39097705922_regression_scope.json        PASS    PASS    PASS     PASS
CYCLE_39116225867_regression_scope.json        FAIL    PASS    PASS     FAIL
CYCLE_39119287975_regression_scope.json        PASS    PASS    PASS     PASS
```

  `--json` emits the machine form; the tool is deterministic across runs
  (asserted byte-for-byte in the suite).

- `cycle_verify.py::regression_set_relation_rows` is the **single** definition.
  `check_regression_set_relation` calls it, so the gate and the matrix can never
  disagree.
- **New ledger check `regression_matrix`** (`check_regression_matrix_matches_diagnosis`)
  recomputes the classification and compares it to what the diagnosis publishes,
  so the next hand-edited list turns the shipped ledger red instead of an
  auditor's re-derivation. Non-vacuity is proven three ways: re-inserting the
  false entry fails it, a duplicated list fails it, a missing artifact fails it,
  and a *later* clean artifact does **not**.

**A refinement, measured rather than assumed:** the two pre-scope artifacts yield
**three** FAIL claims each (claims 1 and 2 fail on *absent* schema/1 and schema/3
fields, not only on the null `scope` block). "Produce that exact claim pair"
describes the *recorded assertion message*, which quoted two of the three failing
lines — not a two-claim ledger. This does not change which artifacts can produce
the recorded message, so the cause-space conclusion is untouched.

**Direction matters, and this cycle learned it the hard way.** The first version
of the check demanded set **equality**, which made this very repair's own
regression run fail its own suite the moment it committed a new clean artifact —
the self-referential class the diagnosis is about. The shipped check enforces
`published ⊆ actually-PASS/PASS` (the false-claim direction) plus completeness as
of `run_id_diagnosing`, and **discloses** later artifacts by name instead of
requiring them back into a historical record. The semantics are stated in the
artifact itself (`list_semantics`).
