## 2. Required fix 1 — pool ownership (code delta, falsification-verified)

**Root cause.** `query_app.POOL` is a module-level `ThreadPoolExecutor` (`query_app.py:63`) created at import time
and shared by the whole interpreter. `serve()` created the HTTP *server*, so it closed that server — but it also
called `POOL.shutdown(wait=False, cancel_futures=True)` on an executor it never created. One in-process `serve()`
call therefore disabled background jobs for the rest of the process.

**Repair.** `product/human_gate_session.py`:

* `serve()` now imports only `make_server` and no longer touches `query_app.POOL`. Its docstring states the
  ownership contract it now obeys (and why, so the next cycle cannot "tidy" it back).
* Process-global teardown moved to the `if __name__ == "__main__":` entry point — the only place that owns the
  interpreter the pool lives in. The CLI keeps its fast cancelled-queue teardown; no in-process caller can be
  poisoned. Verified: `python product/human_gate_session.py --fixture --port 8811 --wait-s 3 --quiet`
  exits **9 in 4.0 s** (no interpreter hang from live pool threads).

**Guard.** New test `product/tests/test_human_gate_session.py::test_serve_does_not_shut_down_the_process_global_job_pool`
asserts both halves of the defect so it cannot return through either route:

1. *mechanism* — after `serve()`, `query_app.POOL.submit(...)` still returns a result;
2. *symptom* — a server started afterwards still answers `/api/query/start` with `phase == "map_ready"` and a
   non-empty decision set.

**Evidence — 13 MVP modules, default collection order, same venv:**

| condition | result |
|---|---|
| base `aae6f90`, before the repair | **8 failed, 227 passed, 1 skipped** (audit reproduced) |
| repair applied | **236 passed, 1 skipped, 0 failed** (237 collected: 236 + 1 skip + the new guard) |
| defect re-injected into `serve()` | **9 failed, 227 passed, 1 skipped** — the 8 original failures **plus** the new guard, which fails on the exact `RuntimeError: cannot schedule new futures after shutdown` |

The repair is load-bearing, and the guard fails on its own — not only through default-order cross-module pollution.
The results tree stayed clean across all three runs (`git status --porcelain -uall -- results/` → 0 non-cache paths).
