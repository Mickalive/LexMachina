## 1. What actually blocked `de-kapitalverletzung`

The question is two-concept: *"Aktive **Fürsorgepflicht** des Arbeitgebers bei einer
**Kapitalverletzung** …"*. Measured on the shipped bundle
(`results/product/gate_packet/38799024807/questions/de-kapitalverletzung.bundle.json`,
134 decisions, by `product/query/concept_coverage.py`):

| query concept | retrieved decisions carrying it |
|---|---|
| `fursorgepflicht` | 23 |
| `arbeitgebers` | 31 |
| `eingriff` | 10 |
| **`kapitalverletzung`** | **0** |
| `uberwachungspflicht` | **0** |

The generative model read 30 sources that cover the first concept and **correctly refused** to
present the second as an answer: *"none of them address the employer's active duty of care
specifically in the context of a capital impairment"*. It cited nothing because **the corpus it was
given does not contain the second concept**. Telling the generator to "cite more" would have put a
citation on a proposition the decision does not contain — the same class of defect this lane was
audited for on the citation channel in run 38766812030.

The split is in the corpus, not in the retrieval of this query. Seven live OpenCaseLaw probes
(`/decisions`, totals as returned upstream, free public source, no paid API):

| probe | total |
|---|---|
| `Kapitalverletzung Fürsorgepflicht` | 124 |
| `Kapitalverletzung` | 108 |
| `Fürsorgepflicht Arbeitgeber Insolvenz Konkurs` | 72 |
| `aktive Fürsorgepflicht Arbeitnehmer Krisenzeit` | 111 |
| `Arbeitgeber Schutzpflicht Kapitalverletzung OR 328` | 115 |
| `Fürsorgepflicht des Arbeitgebers Krisen Art. 323 OR` | 83 |
| `employer duty of care insolvency Art. 328` | 109 |

The employer's duty of care is a real Swiss line (BGE 132 III 257, BGE 132 III 115,
BGE 4A 611/2018, BVGer A-417/2013). The **capital-impairment combination has no on-point decision
in the corpus**; those totals are filled with OR-material and unrelated insolvency decisions.

**Negative result, recorded as such:** no extra retrieval pass was added to chase this concept.
A repair pass would have added off-topic rows without producing authority, and the honest product
behaviour for a missing concept is to *say so with citations for the part that exists*.

## 2. The contract this cycle ships (`product/query/answer_gap.py`)

A sourced answer must cite something, **or it must say what is missing**:

* model cites → the contract does not run (verified no-op on all three live bundles, §4);
* model declines → the product surfaces **what the corpus does cover, quoted verbatim and cited**,
  grouped by the query concept each quote proves, and **names the concepts the retrieved corpus
  does not cover** with their measured row counts;
* nothing quotable in the bundle → the contract **refuses to run** and the bundle stays blocked. An
  uncited answer is better than an invented citation.

Mechanics that keep it honest, all covered by tests:

* quotes are copied **unchanged** from a row's own `regeste`/`full_text` and attributed with that
  row's `decision_id` + citation, so "this decision says this" is string-checkable (and is);
* headnotes outrank body text, rule-stating sentences outrank fact patterns, federal practice
  (BGE/BGer) outranks cantonal, all deterministically;
* a sentence cut by the splitter at an abbreviation (`… des Arbeitgebers (E.`) is **extended to its
  terminator** from the same field, so no jurist ever gets a truncated proposition under a citation;
* a row with only a truncated snippet is skipped rather than quoted mid-sentence;
* the model's own assessment is **kept verbatim** at the top (`superseded_prose`), and the answer is
  marked `degraded` / `concept_coverage_extractive_v1` so it is never presented as the target
  generative path. The UI now says exactly that instead of the old "provider unavailable" note.

Supporting module `product/query/concept_coverage.py`: deterministic DE/FR/IT content-concept
extraction (function words, statute abbreviations, generic legal nouns removed) and per-concept row
coverage, with the same NFKD normalisation as `answer_contract.py` so the two cannot disagree.
Cost on the 134-row bundle: **0.08 s**, single normalisation pass shared with the quote lookup.

## 3. A second blocking defect the live run exposed: one decision, two points

The first live run of this cycle (`de-kapitalverletzung`, 176 decisions) was blocked by
**`citation_duplicates`** — and the cause is not citation text, it is identity:

```
bvger_A-2789_2024          docket A-2789/2024  date 2025-07-04  citation.incoming  pending
bvger_A-2789_2024_d20240318 docket A-2789/2024  date 2024-03-18  citation.incoming  pending
```

The same decision, twice on the same map, under two upstream ids. The shipped 38799024807 bundle
carries the milder form of the same defect (`bvger_A-1979_2024` shell beside the hydrated
`…_d20240326` row, with **two different citation strings for one decision**).

`product/query/pipeline.py::merge_duplicate_identities` now collapses rows that share
(court, docket) and exports `provenance.identity_merge` naming the kept id and every dropped id.
The kept row is chosen deterministically: real evidence beats a shell → a row whose id-embedded date
agrees with its own `decision_date` beats one that contradicts it → better rank → lexicographic id.
Applied to the run-1 bundle: **176 → 174 rows, 0 duplicate citation strings left**; on the shipped
packet it is a **no-op**, and it is a **no-op on the frozen claim bundle** (§5).

### A third defect, found only because 3/3 was reached

The second live run produced all three admissibility files and then **died on a `KeyError`**:
`ready_for_owner_session` read `summary["guards_all_ok"]` one line before it was written. Python
short-circuits, so only a packet where *every* question passed *and* the mode was live reached it —
i.e. the single outcome the ceremony needs — and that packet was lost. Fixed by extracting
`gate_packet.finalize_summary()`, which is now unit-tested for the all-pass live case, the fixture
case, the blocked case, and the guard-failure case (2 new tests in `test_gate_packet.py`).

## 4b. Adopting the accepted Frontier verdict (backlog item 4, partially)

The accepted `frontier-adversarial-discoverability` report (cycle 38794235870, **gate=FAIL**) measured
on the 227-row bundle: counter yield 1.3% against a 2% threshold, every counter row coming from the
**initial retrieval channels**, and `b1_adversarial_channel_rows: 0` — the counter pass had no
channel of its own, so the map could not add contrary authority the ranked list did not already
contain. That is a property of *this product's* counter pass, so the packet now recomputes it per
question instead of waiting for the team's verdict to be read:

```
gate_admissibility.measured.counter_channels / counter_rows_from_citation_channels / counter_yield
warning  counter_authority_has_no_own_channel   (disclosure, never a refusal)
```

On the three live packet questions it reproduces the verdict independently: yields **0.011 / 0.023 /
0.018**, every counter row from `search` (one IT row from `search.language_filter`, one from
`leading_case`), **0 from a citation channel**. The owner card therefore tells the jurist, before
they answer gate question 3, that this pass cannot show them contrary authority the list hid. The
FR question carries one more disclosure — 38/177 rows are in French, the question's own language.
`frontier-map-semantics` has no accepted verdict mounted yet; nothing from it is claimed here, and
the packet only carries the product's own measurements.
