### 2.2 Fixture replay hydration budget

Warming the cache exposed a second, independent defect. `replay_fixture_query`
reused a 40-request **search+hydration** budget for fixture replay. With
`hydrate_top=200` it selected 165 candidates but could only spend ~14 details
before the budget was exhausted, so cached bodies were present and still not
used. `max_requests` is not part of any request key; raising it for an explicit
hydration request does not change which envelopes are read. Verified: the same
7–11 searches, the same candidate ids, and unchanged geometry with 40 vs 400
requests. `product/query/pipeline.py` now adds the requested hydration work to
the budget (2 requests per candidate + 16 headroom) only for the product-cache
replay; the legacy fixture path is untouched.
