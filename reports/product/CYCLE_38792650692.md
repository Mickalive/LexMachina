## 2. Why a packet, and what is in it

Master Prompt §12 asks the human product gate to be answered on *"a SMALL SET of real legal research
tasks"*. The shipped path was one query per owner ceremony (`product/human_gate_session.py`), so a single
session cannot separate *"this map helped me"* from *"this map happened to help on this question"*.

`product/data/gate_packet_questions.json`
(`sha256 32eace355b70edc6a8dcc6cca97ec745b1a1c8985a7afd13668fa752008d34cb`, pinned in
`product/gate_packet.py::PREREGISTERED_MANIFEST_SHA256`) freezes **three real questions before any retrieval
ran against them**:

| qid | lang | area | the question |
|---|---|---|---|
| `fr-bail-entretien` | FR | bail — entretien et résiliation (CP 257d ss.) | *Résiliation du bail pour défaut d'entretien du bailleur : jusqu'où va la jurisprudence, et quelles décisions distinguent le défaut d'entretien grave de la simple négligence ?* |
| `de-kapitalverletzung` | DE | Arbeitsrecht — Sorgfaltspflichten bei Kapitalverletzung (OR 321 ff., EOG) | *Aktive Fürsorgepflicht des Arbeitgebers bei einer Kapitalverletzung: wie weit geht der aktive Eingriff, und welche Entscheidungen begrenzen ihn gegenüber einer blossen Überwachungspflicht?* |
| `it-responsabilita-medica` | IT | responsabilità civile — responsabilità medica (c.c. 2052 ss.) | *Responsabilità del medico per errore terapeutico: quale obbligo di diligenza e quale nesso causale devono essere dimostrati, e quali decisioni escludono la responsabilità?* |

Each carries the **hypothesis it is meant to test** (which branches should become visible), what to look
for, and which counter-authority is needed. The **success rule is fixed in the manifest before results**: a
positive product result only if, on at least two of the three questions, the jurist answers q1 or q3
yes/partly **and names at least one specific decision, branch or exception that was less visible in the
ranked list**; a blanket "yes" with no named authority does not count; a "no" is recorded as a negative
result and is not averaged away.

Anti-tuning is enforced, not promised: `load_manifest()` refuses a manifest whose digest does not match the
pinned one, and `test_editing_the_pre_registration_after_the_fact_is_refused` reproduces the attempt. Each
packet also freezes its own copy of the manifest (`manifest.json` + digest), so editing the canonical file
later cannot re-point a shipped packet at different questions.

## 3. Run-time admissibility — "never ship a frozen defective bundle"

`product/query/gate_admissibility.py::verify_bundle` recomputes the verdict from the bundle in hand, every
time, and reuses the existing product code rather than re-implementing it:
`product.query.bundle.validate_bundle`, `product.replay_bundle.inspect_bundle` (synthetic ids/labels,
required fields, orphan cluster members, dangling relations, citation forensics, field coverage,
path-independent `content_sha256`), and `product.query.pipeline.CITE_CHANNELS`.

**Blocking** — a bundle with any of these is not gate material:

`validate_bundle` errors · `synthetic_decision_ids` / `synthetic_cluster_labels` (the cycle-38759730609
defect) · `missing_required_fields` · `orphan_cluster_member` · `dangling_relation` · `citation_duplicates`
· `citation_channel_seed_refs` · `pending_shell_identity` (the three citation-identity guards the repair
rounds added) · `foreign_source_host` · `map_too_small` (below the MP 100–300 comparative window) ·
`answer_missing` / `answer_cites_nothing` / `answer_cites_off_map_decision` ·
**`source_url_null_on_hydrated_row`**.

**Disclosed, never blocking** (the owner card prints them, so nobody is asked a question the artifact
cannot support): `no_counter_authority` (gate question 3 is unanswerable on such a bundle) ·
`map_is_one_mega_cluster` and `no_relations_on_map` (the two map-semantics weaknesses the director
observed on accepted bundles; `frontier-map-semantics` owns the accepted measurement, so these are numbers
on a card, **not** map-quality claims) · `question_language_underrepresented`.

## 4. Per-query drafts only, and the guards that already exist

`preflight` writes, per question:

* `<qid>.bundle.json` — the served, enriched bundle;
* `<qid>.admissibility.json` — the verdict with every finding and every measured number;
* `<qid>.question.json` — **the per-query draft**: `record_type: "product-gate-packet-question"`, the
  question, its hypothesis, what to look for, the four gate questions, the bundle binding
  (`content_sha256` + `canonical_sha256`), the measured map numbers, every blocking finding, every
  disclosure, the deep link, and the exact finalize command.

It is deliberately **not** a session draft. `human_gate_finalize.validate_draft` refuses it with exit 4
(`test_the_packet_question_file_can_never_be_finalized_as_evidence`), and no packet artifact carries
answers, a `finalized` status or a session record.

`probe_guards()` then exercises the **existing** `human_gate_finalize` guards against each bundle, writing
only into a temp directory that is deleted with it:

| probe | expected | asserted |
|---|---|---|
| finalize a packet question file | exit 4 | ✅ |
| machine session probe on this bundle (simulated, unanswered) | exit 3 + an admissible evidence scan | ✅ |
| simulated record into the canonical evidence dir | exit 8 | ✅ |
| undeclared session into the canonical evidence dir | exit 8 | ✅ |
| a **real, answered, declared** session on *this* bundle | accepted (exit 0), in memory only | ✅ |

So the ceremony is known to work **before** the owner is asked to sit down.

`card --serve` seeds each admissible bundle into the served app's run registry (`seed_runs`) and links
`?run_id=…`, so the jurist works *the artifact that was checked* — not a fresh retrieval that merely looks
similar, which would then bind a session to a different bundle at finalize time. `verify`/`card` re-hash
every artifact: a bundle whose `content_sha256` changed since preflight is blocked as
`bundle_drifted_since_preflight`.

### The UI delta the packet needed

`product/static/query.html` had no deep link, so a three-question ceremony meant three retypings and the
verified bundle was unreachable by URL. `boot()` now parses `?q=`, `?n=`, `?run_id=` once, resumes that
exact run (or runs the question), and otherwise falls back to the previous "resume my last run"
behaviour. `product/dom_shim.js` gained `location`, `URLSearchParams`, `localStorage` and `select.options`;
`product/verify_query_page.js` asserts that a `?run_id=` link resumes **exactly** that run and never
re-retrieves:

```
$ node product/verify_query_page.js results/product/CYCLE_38759730609_bundle.json           -> PASS 25
$ node product/verify_query_page.js results/product/CYCLE_38759730609_bundle.json "?run_id=deadbeef"
    ok - a ?run_id= link resumes exactly that run (deadbeef)
    ok - a ?run_id= link does not re-retrieve a new run                                       -> PASS 25
```

(19 → 25 assertions; none removed or relaxed.)
