## 2. RF1 — "counter authorities" was counting citations

**This is a gate defect, not a rename.** `counter_status` is a provenance field as well as a verdict field. `"cited"` means the generative answer **cited** the decision — the opposite of countering it. The broad `counter_status != "none"` test swept it in anyway.

| | Old published | Corrected | Inflation |
|---|---|---|---|
| demo | 5 | **1** (`ju_gerichte_CC_2021_44`, `candidate-limiting`, evidenced) | 5.0× |
| live | 7 | **2** (both `abstained_unevidenced`) | 3.5× |

Overstating contrary-authority yield makes the Master Prompt's question — *"did the map increase confidence that contrary authority had not been hidden?"* — easier to pass for the wrong reason.

**The live reconciliation is the sharpest evidence.** `generative_audit.status_summary` reads `supporting: 7, limiting: 0, contrary_or_exception: 0`. So the generative audit issued **no limiting and no contrary classification at all**, and the published "7 counter authorities" equals its **supporting** count.

I initially wrote that the old 7 *was* the supporting count by identity. The tool measured `cited` rows = 5 ≠ 7 and falsified it. Per factory-wide requirement 16 the artifact now states which relations hold and records the rest as **unverified** — `supporting(7)` and `cited(5)` are measured at *different stages* and were never shown to be the same set. Either way the old number cannot be a counter count.

**Single source of truth.** `product/query/counter_status.py` is a new **stdlib-only leaf**; `gate_admissibility` imports and re-exports it, so `gate_admissibility.NON_COUNTER_STATUSES` *is* that object (identity contract preserved and asserted). The leaf exists purely for import cost: `human_gate_finalize` is a browser-export CLI and pulling numpy/scikit-learn into it would be a regression. A test asserts the leaf has no heavy imports.

Seven surfaces fixed — `bundle.bundle_summary`, `query_app.run_status`, `query_app._enrich_task`, `human_gate_finalize.bundle_evidence`, `gate_rehearsal._counter_ids`, `slice_smoke`, `offline_slice`. The bare `counts.counter` key was **removed, not renamed**, so nothing can keep reading the inflated number. `offline_slice` had a second, distinct bug: `startswith("candidate")` silently missed `abstained_unevidenced` entirely.

Per audit F3, **both definitions are always published side by side** — and the live slice now reports both, from the product's own run:

```
counter_rows: 1                  # real counter authorities
counter_status_bearing_rows: 5   # provenance, honestly named
```

## 3. RF2 / RF4 — a delta that disagreed with its own inputs

Two defects, one root cause: **a number in a report the measurements do not support.**

- **RF2** — "+7 net new passing tests" published where the measured change was +10 (564 → 574).
- **RF4** — that count was pinned to a **re-probed moving snapshot** (21:30:00Z), already stale against the control plane's 22:24:12Z snapshot when the audit read it. The audit recomputed 162 passed / 1 failed and falsified "163 passed / 13 passed (fixed)".

A timestamp is not a pin. It names an *instant*, not a *tree*: the same command re-run a minute later legitimately differs, so the pin cannot be checked and rots silently.

`product/test_accounting.py` replaces both. It **refuses** rather than guesses — an unparseable log exits non-zero instead of yielding zeros (which is exactly how "+7" could be published against no data), and a pin must name a run id **and** a commit, with the baseline required to be an ancestor of head. | head | `ec622c6` | 39082232157 | 624 | 43 |
| **delta** | | | **+62** | **−2** |

+62 derived, not asserted. The 18 tests reproduce RF2's own case (564 → 574 == **+10**) through the tool, and a test re-derives every delta in the committed artifact from its own two counts.
