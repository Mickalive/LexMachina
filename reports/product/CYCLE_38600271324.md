## 3. Durable evidence for (b): observed, not asserted

`python product/ci_run_evidence.py --run-id 38600271324 --apply` fetched
`GET /repos/Mickalive/LexMachina/actions/runs/38600271324` and wrote the snapshot verbatim:

```
run_id 38600271324 | status in_progress | conclusion null | head_sha 43652aa | created 2026-10-14T16:41:50Z
machine_gate.ready = false
machine_gate.reasons = ["conclusion=None is not 'success'"]
machine_gate.provenance_note = "summary records the lab-branch head ea161e6 that this run executed (run dispatch sha 43652aa)"
```

`machine_gate_ready` stays **false** and is not predicted anywhere in state: the conclusion of a
run is not observable while its own team job is still executing. The next cycle (or the owner)
runs the same command once the run finishes; if and only if `conclusion == "success"` *and*
`summary_ci_38600271324.json` shows `legs_complete` + `all_legs_passed` does the recorder flip
`machine_gate_ready` to `true` and set `evidence_tier = DURABLE_CI_VERIFIED`. Tests pin every
negative path: in-progress run, failed run, incomplete legs, fixture-mode summary, summary from
another run, undocumented foreign sha, missing summary, HTTP 404 → `unresolvable_run_ids`.
`human_gate_ready` is never written by this tool — it stays `false` per (c).

Provenance subtlety found and fixed while building it: a core-lane team job is dispatched on
`main` (`GITHUB_SHA = 43652aa`) and then switches to `lab/product` (`ea161e6`), so the run's REST
`head_sha` is *not* the code that produced the evidence. A naive `summary.head_sha == run.head_sha`
check would have blocked the machine gate forever. The runner now records both
(`run_head_sha`, `head_sha`) and the recorder accepts either the dispatch sha or the lane-branch
head that is documented **for that run id** in `state/product.json`; anything else is refused
(3 tests cover exactly this).
